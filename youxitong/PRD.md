## 1. 产品概述

### 1.1 背景

酒店布草租洗业务涉及酒店、优洗通平台、洗涤厂三类业务主体。酒店需要根据实际送洗量补充干净布草，平台负责客户、价格、资金和履约关系管理，洗涤厂负责备货、出库、配送协作、退污检测和成本结算。现有线下沟通方式容易产生数量口径不一致、价格越权、退款争议和资产难追踪等问题。

### 1.2 产品目标

- 形成“日常有效送洗入库形成额度—酒店补充下单—钱包扣款—工厂履约—酒店收货—退污检测—退款入账”的可追溯闭环，并将首次铺货与首次芯片登记单独标识。
- 让每个角色只看到与其组织、职责和价格口径相关的信息。
- 将酒店销售价与洗涤厂成本价严格隔离。
- 用固定酒店与洗涤站点映射满足一期调度需要，避免引入不必要的智能调度复杂度。
- 为后续 RFID 设备对接、结算账单和商城履约保留清晰的产品边界。

### 1.3 角色与使用端

| 角色 | 使用端 | 核心职责 |
|---|---|---|
| 平台系统管理员 | 平台 Web | 账号、角色、权限、审计和基础设置 |
| 平台运营人员 | 平台 Web | 酒店、洗涤厂、站点、价格、映射、订单、退款、商城和司机范围 |
| 平台财务人员 | 平台 Web | 酒店账户、充值管理、退款核对、工厂结算和资金报表 |
| 酒店管理员 | 微信小程序 | 补充下单、订单与退污、账户与充值、商城和酒店员工 |
| 酒店操作员 | 微信小程序 | 原型默认可日常补充、查看订单和发起退污，不查看精确余额；最终权限待确认 |
| 洗涤厂管理员 | 洗涤厂 Web | 本厂履约、送洗入库、库存、仓储、退污、站点和经营总览 |
| 洗涤厂操作员 | 洗涤厂 Web | 备货、出库、送洗入库、仓库货架和退污检测；送达确认主体待确认 |
| 洗涤厂财务 | 洗涤厂 Web | 本厂成本、结算账单和期间报表 |
| 司机 | 移动端（渠道待确认） | 查看本人负责区域和酒店静态清单 |
| 固定终端操作员 | 洗涤厂固定终端 | 首次芯片入库和租赁备货扫描 |

### 1.4 一期范围

- 平台与洗涤厂 Web 的角色化工作台和业务管理。
- 酒店管理员、酒店操作员微信小程序，以及司机移动端的静态范围清单。
- 固定终端的两个工位模式。
- 补充额度、预存钱包、订单履约、退污退款、简单商城和资金流水。
- 页面必须提供加载、空、错误、无权限和关键操作反馈状态。

### 1.5 一期不做

- 司机抢单、接单、任务状态、路线规划、导航、实时定位和电子签收。
- 动态或智能派单；一期使用固定酒店—洗涤站点关系。
- 在充值渠道确认前固化微信支付或线下核款任一方案；两者均以候选流程评审。
- 复杂商城营销、优惠券、促销和多商家交易。
- 在原型中模拟真实 RFID 设备协议、厂商 SDK 或离线补传能力。
- 司机端消息提醒、使用反馈、租金查询、在线任务与授信额度；其中授信是否需要为待客户确认。

## 2. 全局体验与信息规则

### 2.1 需求可信度标记

| 标记 | 含义 | 展示要求 |
|---|---|---|
| 当前已实现 | 已有系统存在可运行闭环 | 可按当前状态演示，但仍需生产验收 |
| 目标待实现 | 客户目标明确，现有系统尚未完整支持 | 页面保留完整方案并提示不代表已上线 |
| 待客户确认 | 业务口径存在冲突或资料不足 | 不应默认成为最终生产规则 |

### 2.2 数据与隐私

- 原型中的酒店、站点、订单、金额和人员均为交互示例数据，不作为经营统计或真实凭证。
- 不展示客户资料中的真实账号、密码、访问地址和联系方式。
- 酒店用户只能查看本酒店信息；洗涤厂用户只能查看本厂及所属站点信息；司机只能查看本人负责范围。
- 洗涤厂不得看到酒店销售价，酒店不得看到洗涤厂成本价。
- 酒店操作员仅看“余额充足/不足”，不展示精确余额与完整资金流水。

### 2.3 通用交互

- 列表默认展示筛选区、数据表、分页、空状态和错误重试。
- 新增、编辑等录入任务使用抽屉；状态变更、退款审核、确认扣款等高风险操作使用确认弹窗。
- 成功后明确反馈结果并刷新关联数据；失败时保留已填写内容并给出可处理原因。
- 被权限限制的入口不展示；从外部地址进入时显示无权限页，不以空白页代替。
- 所有金额展示币种并保留两位小数；数量必须带计量单位“件”。
- 状态不能只依赖颜色，同时展示状态文字。

## 3. 核心业务规则

### 3.1 补充额度

- 日常业务中，额度由酒店脏布草被洗涤厂有效接收入库的数量形成，不按自然日自动重置。
- 送洗入库记录必须包含来源酒店、站点、布草品类、有效数量、重复或异常数量和额度变动结果，并可从额度明细追溯原批次。
- 下单时按布草品类分别校验可补充额度，不允许某一品类用其他品类额度抵扣。
- 单品本次补充数量不得大于该品类可补充额度。
- 原型暂按“酒店 + 布草品类”展示额度；是否还需细分楼层、批次或站点为待客户确认。
- 新酒店首次铺货、首次芯片登记与日常脏布草送洗是三种不同业务；前两者是否形成可补充额度为待客户确认，不得自动等同于日常送洗。
- 退款成功后是否恢复额度为待客户确认。

### 3.2 价格与资金

- 酒店下单使用酒店合同销售价；同一布草品类可因酒店不同而价格不同。
- 洗涤厂履约与结算使用平台维护的成本价；成本价的维度为待客户确认。
- 下单金额等于各品类数量乘以对应酒店销售价之和。
- 酒店使用预存钱包，余额足够时补充下单并扣款；不足时阻止下单并引导管理员进入充值方式选择。
- 重复提交不得产生重复订单或重复扣款。
- 充值渠道待客户确认：微信支付候选流程为支付成功后入账，线下候选流程为平台财务确认到账后入账；两种流程均须形成可追溯资金记录。

### 3.3 分配与履约

- 每个酒店固定映射一个默认洗涤站点；补充订单自动进入该站点待履约列表。
- 一期不做跨站点动态调度。调整映射只影响新订单，存量订单是否迁移为待客户确认。
- 当前履约主状态为：已派发、备货中、已出库、已送达。
- 各状态由谁操作、能否回退、异常单如何处理需在生产验收前确认。

### 3.4 退污退款

- 酒店必须从已送达订单的原始明细发起退污申请，不得脱离订单新增品类。
- 每个品类申请数量不得超过该订单对应品类的已送达数量减去历史有效申请数量。
- 退污不换货。洗涤厂检测后可按实际情况全部通过、部分通过或全部驳回。
- 通过金额按原订单酒店销售单价计算并退回酒店预存账户。
- 工厂端只看件数和检测处理，不展示酒店退款金额。
- 实物处理建议区分待取回、待检测、部分通过、已通过、已驳回；资金另设未进入退款、待退款、已退款、退款异常，最终状态名称待客户确认。

### 3.5 商城

- 一期商城仅包含分类、商品图片、名称、描述、全平台统一售价、库存和上下架状态。
- 酒店管理员可浏览和加购；酒店操作员是否可购买为待客户确认，原型默认不可见。
- 提交时再次校验库存；商城使用预存余额还是独立支付渠道待客户确认。
- 商城支付、发货、收货、退货与退款流程为目标待实现，未确认前不固化资金口径。

## 4. 平台 Web

### 4.1 平台总览

- 展示业务主体、酒店、站点、待处理订单、待处理退污和资金异常等摘要。
- 统计卡片必须说明统计口径和更新时间；没有真实数据时展示占位说明，不生成虚假经营结论。
- 展示核心闭环状态分布、待办事项和业务边界提醒。

### 4.2 酒店管理

#### 列表字段

- 酒店名称、所属区域、合作状态、默认洗涤站点、账户状态、创建时间。
- 平台财务角色可查看账户余额；平台运营不默认展示精确余额。

#### 筛选与操作

- 支持按酒店名称、区域、合作状态和默认站点筛选。
- 平台运营可新增、编辑、停用酒店，维护楼层与房型基础信息。
- 停用前检查是否存在未完成订单、待处理退款或未结事项；存在时阻止并说明原因。
- 酒店详情展示基本资料、楼层布草配置、价格方案、站点映射、员工和业务记录。

### 4.3 洗涤厂与站点

- 列表展示洗涤厂、站点名称、覆盖区域、负责人、合作状态和当前绑定酒店数。
- 站点从属于洗涤厂，一个酒店一期只绑定一个默认站点。
- 停用站点前必须处理其绑定酒店和未完成订单。
- 洗涤厂管理员只能维护本厂允许范围内的站点信息；跨厂关系由平台运营维护。

### 4.4 订单中心

#### 列表字段

- 订单号、酒店、楼层、洗涤站点、总件数、酒店应付金额、创建时间、当前状态。
- 平台财务可查看销售金额；洗涤厂视图不得复用该金额字段。

#### 筛选与详情

- 支持订单号、酒店、站点、状态和下单日期筛选。
- 详情展示品类明细、下单数量、销售单价、小计、钱包扣款记录和履约时间线。
- 可追踪退污申请，但订单详情不允许直接修改历史数量与价格。
- 异常处理必须记录原因和操作人。

### 4.5 价格与映射

- 酒店销售价按酒店与布草品类维护，必须设置生效时间和启停状态。
- 修改价格只影响生效后新订单，历史订单保留原成交价。
- 酒店—站点映射展示当前关系、生效时间和操作记录。
- 同一酒店在同一有效期内只能有一个默认站点。
- 成本价与销售价分区管理并使用不同权限；任何导出也不得串列。
- 平台运营默认不展示工厂成本价入口；确需查看时必须配置独立授权。

### 4.6 退污退款

- 列表同时展示申请单号、关联订单、酒店、站点、申请件数、检测通过件数、实物处理状态、退款状态和退款金额。
- 平台运营只读查看处理进度，不代酒店申请、不代工厂检测；平台财务负责核对退款入账与异常。
- 详情展示每一品类的申请数量、通过数量、驳回数量、驳回原因和原成交价退款明细。
- 已完成退款不可重复操作；人工修正必须进入审计记录。

### 4.7 财务中心

- 酒店账户展示可用余额、冻结金额如适用、累计充值、累计消费、累计退款和最近变动时间。
- 资金流水展示业务类型、业务单号、收入、支出、变动后余额、发生时间和操作来源。
- 充值渠道为待客户确认：页面分别展示微信支付候选状态与线下核款候选状态，不把任一流程标记为最终方案。
- 若采用线下核款，记录酒店、申请金额、申请人、申请时间、凭证状态、确认人和入账时间；财务确认前二次核对酒店与金额。
- 若采用微信支付，以支付成功结果形成入账流水；支付资料、限额、退款和异常处理规则待确认。
- 已入账记录不可直接删除，只能按财务制度进行冲正。

### 4.8 工厂结算

- 按洗涤厂和结算期间汇总有效履约数量与成本金额。
- 结算周期为月结或半月结，最终口径待客户确认。
- 目标状态建议为待生成、待核对、已确认、已结算、已作废，需客户确认后落地。
- 账单详情必须可追溯至订单与品类，但不得带出酒店销售价。

### 4.9 商城管理

- 分类支持名称、排序和启停；存在上架商品时不可直接停用分类。
- 商品展示名称、分类、主图、描述、统一售价、库存、上下架状态和更新时间。
- 上架前必须校验名称、分类、价格、库存和图片完整。
- 库存为零时自动显示售罄，不允许继续提交订单。

### 4.10 司机范围、账号权限与审计

- 司机范围按人员维护负责区域和酒店清单，不形成配送任务。
- 账号必须绑定组织与角色；停用后立即失去登录和业务权限。
- 权限以角色为基础，可按组织范围收敛；不允许酒店账号访问其他酒店。
- 审计日志展示操作时间、操作人、组织、模块、动作、对象和结果；敏感值按规则脱敏。

## 5. 洗涤厂 Web

### 5.1 工厂总览与待办

- 展示本厂站点数、待备货、待出库、待检测退污和结算摘要。
- 所有金额均为本厂成本口径；不得展示酒店合同价、酒店余额或平台毛利。
- 操作员工作台优先展示可以立即处理的订单和退污单。

### 5.2 履约订单

- 列表展示订单号、酒店、楼层、所属站点、件数、创建时间、状态和当前待办。
- 详情展示品类与数量、备货进度、出库信息和履约时间线，不展示酒店销售金额。
- 操作员按权限执行开始备货和确认出库；送达或收货由谁确认待客户决定，原型不提供可执行的确定按钮。
- 状态操作需二次确认；不满足前置状态时按钮禁用并说明原因。

### 5.3 送洗入库与额度变动

- 洗涤厂接收酒店日常脏布草后，按酒店、站点和布草品类记录有效入库数量。
- 重复芯片、错酒店、错品类和不可识别事件进入异常列表，在处理完成前不计入有效额度。
- 有效入库形成对应酒店、对应品类的额度增加记录；额度明细可追溯入库批次、原始数量和异常处理。
- 新酒店首次铺货、首次芯片登记与日常送洗分开标识；前两者是否形成额度为待客户确认。

### 5.4 布草库存与 RFID

- 库存按站点和布草品类展示可用、占用、累计入库和异常数量。
- 当前系统以扫描事件聚合展示库存，不代表已具备每个芯片的完整资产状态机。
- 目标能力包括芯片唯一性、重复扫描拦截、异常记录和资产明细，依赖硬件协议确认。
- Web 端只查看与处理异常，批量扫描在固定终端完成。

### 5.5 退污检测

- 检测页展示关联订单、酒店、品类、申请数量、已检测数量和状态。
- 每一品类录入通过数量与驳回数量，两者之和不得超过申请数量。
- 驳回数量大于零时必须填写原因；支持部分通过。
- 提交后平台按通过数量计算退款，工厂端只展示检测结果。

### 5.6 物流协作与仓库货架

- 物流协作记录出库与线下配送交接，不向司机生成在线任务；收货确认主体、差异处理和签收凭证待客户确认。
- 仓库按本厂站点、仓区、货架和布草品类展示容量、当前数量、备货占用、可用余量和状态。
- 工厂角色只能查看本厂及所属站点的物流、仓库和货架数据。

### 5.7 站点、经营与结算

- 工厂管理员查看本厂站点资料和绑定酒店，超出权限的映射调整提交平台处理。
- 经营报表按期间、站点、酒店和品类查看订单件数与成本金额。
- 工厂财务查看本厂结算账单、成本明细和期间汇总，只读访问原始订单。

## 6. 酒店管理员微信小程序

### 6.1 首页补充

- 顶部展示酒店名称、当前楼层、补充记录入口、账户状态和额度说明。
- 先选择楼层，再展示该楼层适用品类；是否按楼层隔离额度待客户确认。
- 每个品类展示图标、名称、酒店销售单价、可补充额度和数量步进器。
- 数量默认零；加减步长为 1，不得小于零或大于可补充额度。
- 底部实时汇总预计扣款与总件数；无选择时确认按钮禁用。
- 提交前再次校验额度、余额、价格和站点映射，成功后展示订单号与去向。

### 6.2 订单与退污

- 订单列表展示订单号、创建时间、件数、金额和状态，支持按状态切换。
- 详情展示楼层、品类、数量、成交单价、扣款金额和履约时间线。
- 只有已送达且仍有可申请数量的明细显示“申请退污”。
- 退污页按原明细选择数量、填写原因和补充说明；提交后可查看检测进度与退款结果。

### 6.3 账户与充值

- 展示可用余额、累计充值、累计消费、累计退款和最近资金流水。
- 余额不足时进入充值方式选择，分别展示微信支付与线下核款两套候选方案。
- 微信支付候选流程在支付成功后入账；线下候选流程在平台财务确认到账后入账。
- 页面必须明确“渠道待确认”，充值方式、限额、凭证、到账时效与异常处理以客户确认结果为准。

### 6.4 商城与员工

- 商城支持分类浏览、商品详情、购物车和提交时库存校验。
- 商城支付渠道以及发货、收货和售后状态标记为待客户确认或目标待实现。
- 员工管理展示姓名、角色、手机号脱敏、状态和最近使用时间。
- 管理员可新增、编辑和停用酒店操作员；被停用人员不可继续操作。

## 7. 酒店操作员微信小程序

- 本节为原型默认方案，不代表客户已确认最终权限。
- 原型默认可使用补充下单、查看合同单价与订单金额、订单查看、已送达订单退污申请和个人中心；这些能力均待客户确认。
- 补充页不展示精确余额，仅展示“余额充足/余额不足”。
- 不展示账户流水、充值确认、商城、员工管理和平台配置。
- 若余额不足，提示联系酒店管理员处理，不直接开放财务能力。
- 其他补充额度、订单和退污规则与酒店管理员一致。

## 8. 司机移动端

- 司机最终使用微信小程序、Android 应用或两者并存待客户确认，原型以通用移动端画布表达。
- 首页展示本人所属配送组、负责区域和负责酒店数量。
- 一期已确认的最小清单字段为负责区域和酒店名称；地址、联系人、默认站点等附加字段涉及信息最小化，待客户确认。
- 一期为固定范围只读清单，不提供搜索、日期切换、任务状态、接单、路线、导航、定位或签收。
- 无负责酒店时展示空状态并提示联系平台运营调整范围。

## 9. 洗涤厂固定终端

### 9.1 通用要求

- 登录后仅提供“首次芯片入库”和“租赁备货”两个工位。
- 页面明确显示当前工位、站点、操作员、设备连接状态和演示/真实设备状态。
- 未连接设备时可进入交互演示，但必须明确“不写入真实芯片数据”。
- 设备未连接时真实提交按钮必须禁用；若提供演示提交，按钮和反馈必须明确为不写入数据。
- 扫描结果区同时展示有效、重复和异常数量，并保留异常明细处理入口。

### 9.2 首次芯片入库

- 先选择站点与布草品类，再开始批量扫描。
- 每个芯片只能有效入库一次，重复扫描不计入有效数量。
- 提交前展示品类、有效数量、重复数量和异常数量摘要。
- 首次入库是否直接形成酒店补充额度为待客户确认，因此原型不自动承诺额度变化。

### 9.3 租赁备货

- 先选择待备货订单，再按订单品类与数量扫描芯片。
- 扫描数量不得超过订单待备货数量；错品类和重复芯片进入异常列表。
- 达到订单数量后继续扫描不得增加有效数量，超量记录进入异常。
- 达到要求后允许完成备货，并将订单推进到下一状态。
- 中途退出、设备断开和离线数据处理规则需待硬件方案确认。

## 11. 空、错误与异常状态

- 空列表说明当前筛选下无数据，并提供清除筛选或返回全部入口。
- 网络或服务异常保留当前条件，展示重试按钮和简短原因。
- 余额不足展示缺口并引导酒店管理员发起充值；酒店操作员仅提示联系管理员。
- 额度不足明确指出品类、当前额度和已选数量，不自动修改其他品类。
- 站点映射缺失阻止下单，并提示联系平台运营处理。
- 价格未配置或已失效阻止下单，不以零元订单替代。
- RFID 设备断开时禁止真实提交；演示模式必须与生产操作视觉区分。

## 12. 核心验收标准

### 12.1 补充闭环

- 洗涤厂日常送洗入库按酒店与品类记录有效、重复和异常数量；只有有效数量形成可追溯额度变动。
- 新酒店首次铺货和首次芯片登记不自动复用日常送洗规则。
- 酒店选择楼层和多个品类后，系统逐项校验额度并实时计算件数与金额。
- 余额充足时只生成一笔订单和一笔扣款；重复点击不会重复扣款。
- 余额、价格或映射不满足时不生成订单，并给出角色可处理的下一步。
- 订单自动进入固定洗涤站点，洗涤厂可推进备货与出库；送达确认主体按客户最终规则实现。

### 12.2 退污闭环

- 退污只能从已送达订单明细发起，数量上限正确扣除历史有效申请。
- 工厂支持部分通过并要求填写驳回原因。
- 退款仅按通过数量和原成交价计算，成功后产生可追溯的账户流水。
- 检测状态与退款状态分别展示，检测通过后仍可识别待退款、已退款和退款异常。
- 工厂全程看不到酒店销售价和退款金额。

### 12.3 角色隔离

- 若客户采用原型默认的酒店操作员方案，该角色无法看到精确余额、账户流水、商城和员工管理；最终能力以确认后的权限矩阵为准。
- 洗涤厂任何角色无法看到酒店合同销售价。
- 司机只有本人负责范围清单，页面不出现任务状态、路线和定位能力。
- 固定终端只有两个工位，不出现平台配置或财务功能。

### 12.4 状态与可用性

- 关键列表均可演示正常、空、错误和无权限状态。
- 所有关键操作有禁用、确认、成功或失败反馈。
- Web、酒店小程序、司机移动端与固定终端在各自目标画布上信息完整，无横向溢出和遮挡。

## 13. 待客户确认事项

1. 新酒店首次铺货与首次芯片登记是否形成补充额度；日常送洗经有效入库形成额度的起算时点。
2. 房间布草基准采用“房间数 × 4”还是“床位数 × 3”，或按品类分别配置。
3. “布草上限”“当前库存”“可补充额度”的正式定义与计算关系。
4. 补充额度是否只按酒店与品类，是否还需细分楼层、批次或站点。
5. 退污退款成功后是否恢复对应品类补充额度。
6. 酒店充值采用微信支付、线下核款还是两者并存；各渠道限额、凭证、审核、异常和预计到账时效。
7. 酒店操作员是否允许退污申请、是否允许查看单价、是否允许商城购买。
8. 司机端最终形态是微信小程序、Android 应用，还是同时支持。
9. 补充订单完整状态、每个状态操作者、回退与取消规则。
10. 退污检测时效、超时提醒与争议处理规则。
11. 洗涤厂成本价按工厂、站点、酒店还是品类组合维护。
12. 工厂最终按月结还是半月结，确认、开票和付款流程如何衔接。
13. 商城使用预存余额还是独立支付渠道，以及是否需要发货、收货、退货、退款和物流信息。
14. 站点映射调整是否影响已经生成但尚未履约的订单。
15. RFID 设备厂商、协议、芯片编码规则、并发扫描和离线补传要求。
16. 历史芯片和库存数据是否迁移，迁移后的追溯范围。
17. 酒店收货由谁确认，是否需要数量复核、差异处理或签收凭证。

## 14. 需求来源与边界说明

- 本文基于客户会议纪要、业务资料、一期产品需求和现有原型综合整理。
- 会议与资料中的事实优先用于确认业务主体、角色、价格隔离、固定映射、退污不换货和司机一期边界。
- 现有系统状态用于标识“当前已实现”，不自动等同于最终客户验收口径。
- 对资料冲突或缺失项统一列入“待客户确认”，研发不得在未确认前固化为不可逆规则。
- 本文面向产品评审与开发理解，专注业务、交互、数据展示、权限与验收，不包含技术实现方案。
