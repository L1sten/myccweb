# 优洗通全角色业务原型开发交接说明

## 1. 交付内容

| 文件 | 用途 |
|---|---|
| `index.html` | 多角色、多端统一交互原型入口，内嵌可下载 PRD |
| `PRD.md` | 面向产品、前端、后端和测试的业务需求基线 |
| `styles.css` | 原型视觉系统、端形态与响应式样式 |
| `app.js` | 角色切换、页面渲染和关键业务交互 |
| `sessions.md` | 稳定发布记录 |
| `开发交接说明.md` / `开发交接说明.html` | 本交接说明的 Markdown 与 HTML 两种格式，前后端共同使用 |

## 2. 产品端与角色

- 平台 Web：平台系统管理员、平台运营人员、平台财务人员。
- 洗涤厂 Web：洗涤厂管理员、洗涤厂操作员、洗涤厂财务。
- 酒店微信小程序：酒店管理员、酒店操作员。
- 司机移动端：负责区域与酒店静态清单，微信小程序或 Android 载体待确认。
- 洗涤厂固定终端：固定终端操作员。
- 原型顶部“评审角色”仅用于评审切换，不代表生产登录方案。

## 3. 开发主链路

1. 酒店日常脏布草经洗涤厂有效接收入库后形成分品类补充额度；首次铺货和首次芯片登记单独标识，是否形成额度待确认。
2. 酒店选择楼层与布草品类，系统校验额度、合同销售价、钱包余额和默认洗涤站点。
3. 校验通过后生成一笔补充订单与一笔钱包扣款，订单自动进入固定站点。
4. 洗涤厂执行备货与确认出库；送达或收货确认主体、差异处理和凭证待客户确认。
5. 酒店从已送达订单明细发起退污；洗涤厂可全部、部分通过或驳回。
6. 平台按检测通过数量与原成交价退款至酒店预存账户。

## 4. 必须共同遵守的业务红线

- 酒店销售价与洗涤厂成本价必须在查询、详情、导出、日志和报表中全部隔离；工厂数据面不返回敏感价格字段。
- 原型默认酒店操作员不查看精确余额、完整资金流水、商城和员工管理；最终能力以客户确认后的权限矩阵为准。
- 每个布草品类独立校验额度，不允许跨品类抵扣；额度不按自然日自动重置。
- 重复提交不得产生重复订单、重复扣款或重复退款。
- 退污必须关联已送达订单明细；退污不换货，只按实际通过数量退款。
- 酒店与洗涤站点一期使用固定映射，不做智能调度。
- 司机一期只有本人负责区域与酒店静态清单，不做任务、路线、定位、导航和签收。
- 固定终端一期只有首次芯片入库与租赁备货两个工位；没有真实硬件协议前不得假定芯片状态。
- 充值渠道和商城支付方式待客户确认，不得把微信支付、线下核款或预存余额任一方案固化为确定规则。

## 5. 页面实现优先级

### P0

- 角色与组织权限隔离。
- 酒店补充下单、额度与钱包原子校验。
- 日常送洗入库、异常事件和额度变动追溯。
- 固定站点分配与工厂履约状态推进。
- 已送达订单退污、工厂检测和钱包退款。
- 平台酒店、站点、销售价与成本价维护。
- 关键业务审计与空、错误、无权限状态。

### P1

- 微信支付与线下核款两套充值候选流程；客户确认后只实现选定方案。
- 工厂库存聚合与 RFID 异常记录。
- 简单商城、员工账号与司机负责范围。
- 本厂成本报表与结算试算。

### P2 / 客户确认后

- 正式结算账单状态、开票与付款流程。
- 商城发货、收货、物流、退货与退款。
- RFID 设备协议、离线补传与历史资产迁移。

## 6. 前端实现提示

- Web 采用信息密集表格、筛选、抽屉、确认弹窗和状态时间线；移动端采用微信小程序组件与安全区布局。
- 顶部“页面状态”可以切换正常、空、错误和无权限，是验收时必须覆盖的状态清单。
- 所有金额保留两位小数；数量显示“件”；状态文字不能只依赖颜色。
- 原型示例数据仅用于交互评审，开发环境初始化数据也必须与真实客户数据隔离。
- 酒店小程序正式实现使用 uni-app 与微信小程序技术栈，并按酒店管理员、酒店操作员收敛菜单与数据。
- 司机最终使用微信小程序还是 Android 应用待客户确认；不要因原型使用手机画布就锁定技术载体。

## 7. 后端实现提示

- 对角色、组织、酒店、洗涤厂和站点做服务端数据权限校验，不能只依赖前端隐藏。
- 下单应把额度扣减、钱包扣款、订单创建和站点分配视作同一业务事务，并提供幂等保护。
- 日常送洗入库应保存有效、重复与异常事件，额度增加必须关联原始入库批次；首次铺货不得默认复用该规则。
- 退款应保存原订单明细、申请数量、通过数量、原成交价、退款金额和资金流水之间的可追溯关系。
- 历史订单保存成交快照，新价格生效后不得回写历史价格。
- 任何工厂侧返回结果不得包含酒店销售价、酒店余额或平台毛利字段。
- RFID 接入前先冻结芯片编码、设备协议、重复判定、异常处理和离线补传规则。

## 8. 联调与验收建议

- 使用同一组业务样例串联酒店小程序、平台 Web、工厂 Web 和固定终端，不按前后端拆开验收。
- 核心样例：云栖酒店 8F 补充被套 40 件、床单 60 件、浴巾 20 件，示例应付 ¥706.00。
- 验证余额不足、额度不足、价格缺失、站点映射缺失和重复提交均不会生成半成品订单。
- 验证送洗入库异常不增加额度，且额度变动能回查来源批次。
- 验证工厂履约与退污页面不出现酒店销售金额。
- 验证部分退污只退通过数量，并产生唯一退款流水。
- 验证全部角色的正常、空、错误和无权限页面。

## 9. 上线前必须确认

- PRD 第 13 章列出的 17 项待客户确认事项必须逐项形成书面结论。
- 重点阻断项：额度形成与退款后恢复、订单完整状态与回退、收货确认、成本价维度、结算周期、酒店操作员权限、商城履约范围、RFID 协议。
- 未确认项不得以原型示例值直接固化为生产规则。

## 10. 账号与敏感信息

- 公共原型不包含真实客户账号、密码、访问地址和联系方式。
- 原型无需业务账号登录，通过顶部角色选择器评审不同权限。
- 开发、测试和生产账号由项目负责人通过安全渠道分别提供，不写入公开交接文档或代码仓库。
