2. 产品端与角色

  • 平台 Web：平台系统管理员、平台运营人员、平台财务人员。
  • 洗涤厂 Web：洗涤厂管理员、洗涤厂操作员、洗涤厂财务。
  • 酒店微信小程序：酒店管理员、酒店操作员。
  • 司机移动端：负责区域与酒店静态清单，微信小程序或 Android 载体待确认。
  • 固定终端：固定终端操作员。
  • 顶部“评审角色”只用于原型评审，不代表生产登录方案。

3. 开发主链路

  1. 日常脏布草经洗涤厂有效接收入库后形成分品类额度；首次铺货和首次芯片登记单独标识并待确认。
  2. 酒店选择楼层和品类，校验额度、合同价、钱包余额与默认站点。
  3. 生成唯一订单和扣款，订单进入固定站点。
  4. 洗涤厂依次执行已派发、备货中和已出库；送达确认主体待确认。
  5. 酒店从已送达明细发起退污，工厂可全部、部分通过或驳回。
  6. 平台按通过数量与原成交价退款到预存账户，并单独记录退款状态。

4. 业务红线

  • 酒店销售价与工厂成本价在列表、详情、导出、日志、报表中全部隔离，工厂数据面不返回敏感价格字段。
  • 原型默认酒店操作员不查看精确余额、资金流水、商城和员工管理；最终权限待客户确认。
  • 品类额度独立校验且不按自然日重置；所有写操作具备幂等保护。
  • 退污必须关联已送达订单；退污不换货，只按实际通过数量退款。
  • 一期固定酒店—站点映射；司机只看静态范围；终端仅两个工位。
  • 充值与商城支付渠道待客户确认，不固化微信支付、线下核款或预存余额任一方案。

5. 页面实现优先级

P0

  • 角色与组织隔离、补充下单、钱包与额度原子校验。
  • 日常送洗入库、异常事件和额度变动追溯。
  • 固定站点分配、工厂履约、退污检测和钱包退款。
  • 酒店、站点、价格维护，业务审计与异常状态。

P1

  • 微信支付与线下核款两套充值候选流程；客户确认后实现选定方案。
  • 库存聚合、RFID 异常、简单商城、员工账号、司机范围、成本报表与结算试算。

P2 / 客户确认后

  • 正式结算、商城履约售后、RFID 硬件与历史资产迁移。

6. 前端实现提示

  • Web 使用表格、筛选、抽屉、确认弹窗与时间线；移动端使用微信小程序组件与安全区。
  • “页面状态”提供正常、空、错误、无权限四类验收样例。
  • 金额保留两位小数，数量带“件”，状态不得只依赖颜色。
  • 酒店小程序正式实现使用 uni-app 与微信小程序技术栈，并按管理员和操作员收敛菜单和数据。
  • 司机最终使用微信小程序还是 Android 应用待确认，不因原型画布锁定载体。

7. 后端实现提示

  • 服务端校验角色、组织、酒店、工厂与站点权限。
  • 额度扣减、钱包扣款、订单创建、站点分配组成同一事务，并提供幂等保护。
  • 日常送洗入库保存有效、重复与异常事件，额度增加关联原始批次；首次铺货不默认复用该规则。
  • 退污明细、检测结果、原成交价、退款与流水必须可追溯。
  • 历史订单保存成交快照；工厂侧结果不得含酒店销售价、余额或平台毛利。

8. 联调与验收

  • 用同一业务样例贯穿小程序、平台 Web、工厂 Web 与终端，不按前后端拆开验收。
  • 核心样例：云栖酒店 8F 补充被套 40、床单 60、浴巾 20，共 120 件、¥706.00。
  • 验证送洗入库异常不增加额度，额度变动可回查来源批次。
  • 验证余额、额度、价格、映射和重复提交异常不会形成半成品订单。
  • 验证工厂不见酒店销售金额、部分退污正确退款、四类页面状态完整。

9. 上线前确认

PRD 第 13 章 17 项待确认事项应逐项形成书面结论，重点包括额度形成与恢复、订单状态、收货、成本维度、结算周期、操作员权限、商城范围和 RFID 协议。未确认项不得把原型示例值直接固化为生产规则。

10. 账号与敏感信息

  • 公共原型不包含真实客户账号、密码、访问地址或联系方式。
  • 原型无需业务登录，通过顶部角色选择器评审权限。
  • 开发、测试、生产账号由负责人通过安全渠道分别提供，不写入公开文档或代码仓库。
