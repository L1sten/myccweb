  • 独立集成入口 /api/integration/v1，使用单独 Bearer 凭据与固定工厂范围，默认未启用；不是用户登录 token，也不是设备 SN。调用者不能通过传参扩大工厂权限；真实凭据放运行环境，不写文档或代码。

  • 请求：external_event_id、action、site_id、occurred_at（Asia/Shanghai）及 items 必填；业务相关的 hotel_org_id、floor_id、order_id、refund_order_id 按动作提供，actor_name 必填，仅记录第三方操作人说明；真实授权身份是凭据对应的 source_id，不由该姓名决定。请求体上限256KiB；items 每批1至1000条，含 epc；登记动作同时提供 sku_id。
  • 上下文校验：REGISTER 及库内四动作不接受 hotel_org_id/floor_id/order_id/refund_order_id，库内事件沿用前序归属；V1.9.4 调整 DAILY 要求酒店及有效楼层，不接受订单或退污编号；REFUND 选择退污申请，原订单自动派生，不接受另选订单。

  • 结果状态 COMPLETED 或 NEEDS_REVIEW。缺前序、旧发生时间等进入待核对，返回原因，不形成有效轨迹、不改变资产和资金；调用方应查询原批次结果，不把接收成功当业务完成。
  • 同来源事件编号重试时，按提交 DTO 序列化内容的哈希比对；相同内容返回原结果，同号改内容返回409。重试应保持原提交内容；EPC 大小写或条目排序变化可能改变哈希，不保证视为相同事件。越权工厂返回403，不创建他厂记录。普通流转未知 EPC 不自动建档；登记也不能覆盖其他工厂／品类归属。
  • DISPATCH/DELIVERY 部分芯片成功仅更新逐件状态，整单全部 EPC 有效确认后才推进订单；首次可靠送达时间取全单有效 occurred_at 最大值，既有可靠送达时间不覆盖，24小时退污期限不延长。
  • 资产流转、订单数量、酒店／楼层额度、退污和账本在业务事务内一致；失败整体回滚。注册不授额，备货不重复扣额度，退污全齐后按历史价格一次退款／结算扣减。事件重试、查单和并发不能重复处理资金。

额度与历史衔接

  • 可下单量＝min（配置上限，max（0，累计日常入库＋累计退污入库－未出库订单占用－累计出库））。不设期初可用量或核定入口，不从历史可用额度、旧芯片登记或无法归属的记录自动授额。
  • 切换时保留原额度账本；额度上限承接旧配置，新循环入库及订单计数从零开始。旧单仍可履约，既有订单不再次计入新订单扣减；原历史退款不重放。上限本身不授予可下单量。
  • 示例：上限至少50、初始有效日常入库50且未下单，可下单50；新下单40后为10；备货40只增加累计出库、仍可下单10；退污实际入库5后为15。
  • GET /api/admin/hotels/{hotelId}/inventory-quotas 返回启用品类、cap_quantity、inbound_quantity、ordered_quantity、available_quantity、版本及保留的历史计数字段。POST .../quota-policy 只接受品类、上限、版本和幂等键，不接受期初或目标可用量；原直接调整入口拒绝新写入。
  • GET /api/factory/inbound-options 返回本厂酒店、站点和品类；日常回收须校验有效承接站点。POST /api/factory/linen-inbounds 登记酒店、站点、品类数量、备注和幂等键。GET /api/factory/linen-inventory?hotel_org_id=... 返回本厂累计日常入库、退污入库、成功备货出库；酒店全局可下单量由服务端提供，不能从本厂局部统计自行计算。
  • 酒店额度表按“品类（含单位）、额度上限、日常入库、退污入库、累计入库、未出库占用、累计出库、可下单量”展示；仅上限可编辑。工厂操作员入库、租赁备货页移除酒店累计量区块及其独立请求，保留登记表单、当前订单进度与退污应入／已入／剩余数量；底层统计接口保留。
  • 酒店额度跨楼层、换厂延续；入库及新订单更新与额度流水同事务，锁和幂等约束防止并发超额。芯片登记保留，不自动变成酒店日常入库。

整单退污与金额

  • 酒店新入口 POST /api/hotel/refund-orders 接收订单、必填原因、幂等键及多条订单明细数量；旧单明细提交入口返回升级提示。服务端检验首次送达时间、24小时截止、正整数、原单归属与数量、一单一次；同键同内容返回原申请，不同内容冲突。驳回也不恢复申请机会。
  • /api/hotel|admin|factory/refund-orders 列表、详情统一返回主单及明细，workflow=INBOUND 表示新整单流程，LEGACY 表示历史单明细流程。状态为待确认 PENDING、待入库 AWAITING_INBOUND、完成 APPROVED 或驳回 REJECTED。
  • 工厂 POST .../{id}/confirm 仅接收同意/驳回及备注；新流程不接收修改后的数量，驳回原因必填。确认不入账、不恢复额度。
  • POST /api/factory/refund-orders/{id}/receipts 按原站点及申请明细登记分批入库，服务器限制剩余量。每批增加额度；全部入齐同事务将原销售价退款入酒店钱包、记录通过量并按原成本快照计入工厂扣减。整单只生成一次资金入账，失败全部回滚。
  • 新旧申请共同参与原有结算净额聚合，原订单金额不覆盖。历史部分通过仍展示真实通过数量及已入账金额，不套用现价或申请量。工厂响应不包含酒店售价、退款金额、余额或平台毛利。
  • 订单新增首次送达时间、截止时间、可申请状态、不可申请原因及是否有退污；旧单无可靠送达时间禁止新申请，既有申请按历史流程处理。

3. 酒店、工厂与布草的真实模型

  • 酒店与洗涤厂统一在对应酒店或工厂档案建档。酒店填写名称、区域、地址和首个管理员，不创建默认楼层；工厂仅填写名称和首个管理员，不要求或自动创建首站点、区域或地址。
  • 工厂建档后可暂时没有站点，站点从工厂列表“站点”入口的独立管理弹窗新增。新增站点填写名称、区域和地址；配置启用站点及酒店服务关系后才能承接新单。工厂原建档请求中的站点字段为兼容旧请求保留，已不用于生成站点。
  • 酒店楼层为轻量归属信息，按名称、顺序、状态维护；每次新增一条，同酒店名称唯一。无启用楼层可无楼层下单；有启用楼层时必须选择，切换仅改变本次订单归属，不清空已选数量。
  • 布草 SKU 为平台共享品类。酒店价格按“酒店＋SKU”，工厂成本按“洗涤厂＋SKU”，同厂各站点共用成本。是否改为站点独立成本仍待业务确认；本轮没有迁移价格或重算历史资金。
  • 服务关系为“酒店 → 承接洗涤厂＋具体工厂站点”。一个工厂可有多个站点，一个站点可服务多个酒店，一家酒店当前最多关联一个承接站点；更换工厂必须清空旧站点。
  • “酒店档案”“工厂档案”维护模块只选择既有档案；组织资料与成员在对应酒店或工厂档案维护，列表分别提供“详情”“成员”“编辑”：详情只读描述卡，成员独立弹窗，编辑独立表单。工厂列表“详情”以描述卡和只读列表展示工厂及站点信息，“站点”独立弹窗维护站点；“酒店档案”列表分别进入只读详情、独立楼层管理、配置或更换选择、解绑确认及受保护删除确认；详情展示酒店、楼层及承接工厂/站点，不含维护按钮，不重建独立服务关系菜单。
  • 逐件 RFID 布草资产、芯片唯一性、重复初始化保护、酒店实物绑定或换绑以及脏布草扫描自动授额尚未形成完整闭环。不能将选择品类或登记备货理解为逐件布草已经绑定站点或酒店。

4. 下单、备货、出库与交付

  • 酒店提交补充订单时校验有效楼层、酒店协议价、工厂成本、启用承接关系、品类额度与预存余额。订单创建、额度扣减和余额扣减整体成功或失败，正常新单直接进入 DISPATCHED（已派单／待备货）。
  • 订单保存工厂、站点、酒店地址、名称及价格快照。后续更名、停用、解除或变更服务关系仅影响新订单，不重分配旧单、不重算历史价格。
  • 终端租赁备货先选择本站点待备货订单，再选择订单品类。order_id 表示关联订单，business_reference 是独立采集批次幂等编号；同订单可多个 SKU、多批次采集，不再将二者混为同一字段。
  • 后端锁定订单并核对所属工厂、站点、状态、品类与累计数量。跨厂、跨站、非订单品类、超计划数量及出库后追加均拒绝。同厂同批次同内容重试返回原事件，改变内容复用编号拒绝；编号保留前导零，仅裁剪首尾空白。
  • 工厂履约依次为 DISPATCHED → PREPARING → OUTBOUND → DELIVERED。进入 OUTBOUND 前，每一个订单 SKU 的累计有效备货数量必须等于计划数量，缺任何一个品类均拒绝出库；司机不承担送达确认。
  • 已停用工厂或站点不接新业务，但允许其原有待备货订单继续履约；订单品类之后停用也不阻断原单备货。首次芯片入库仍要求启用品类及有效站点。已成功采集的相同批次在出库后重试不重复计数，新增批次不允许。
  • 终端事件不自动推进订单状态、不自动授予酒店额度。工厂仓库仍按首次入库与租赁备货事件汇总：累计入库减累计备货可能为负，当前没有逐件实物库存不足拦截；出库数量门禁不等于实物库存闭环。
  • 酒店仅对已送达订单的一条明细申请退污。工厂可全额、部分同意或驳回；按确认数量和原酒店成交价一次退款至预存余额，不恢复布草额度。

  • 商品图片选填，选择 PNG 或 JPEG 文件，支持预览、更换和移除，不再输入图片 URL。正式上传 POST /api/admin/store/images 接收 multipart 文件，服务端识别真实内容，限制 1MB、宽高不超过 2048 像素，重编码为 PNG 并生成随机文件名。
  • 原型仅在浏览器本地读取文件展示预览；真实项目返回 /media/store/{uuid}.png，上传要求鉴权。图片处理或上传中阻止商品保存；失败保留既有图片与其他输入，未上传使用占位图。
  • 正式项目使用 PRODUCT_IMAGE_DIRECTORY 配置持久目录、Compose 的 product-images 卷及 Nginx/Vite 图片代理。小程序从合法 HTTPS API 源推导图片域名，并需配置合法下载域名；原型预览不验证这些部署条件。
  • 商品名称、说明、售价和初始库存仍按现有业务校验；商品售价输入与列表均以元展示，最多两位小数且须大于零。当前没有上下架、补库存、物流、签收或售后功能。
  • 商品无商城订单引用时可删除；已被商品使用的种类不可删除。种类管理与商品删除均有确认、提交中状态和失败原因。
  • 商城下单继续原子校验商品、库存和酒店余额，生成订单、扣库存与扣余额，重复提交不重复扣减；当前订单创建后为已支付，不代表存在物流闭环。

6. 历史充值流程记录（新业务以当前交付为准）

  • 原型演示酒店管理员提交线下充值申请 → Web 平台管理员或财务绑定银行流水审批 → 通过后更新演示余额及账本。提交和驳回不入账，不提供微信支付。
  • 金额以元输入，大于零且最多两位小数，12.34 元精确转换为 1234 分；拒绝超精度而非静默舍入。真实服务继续使用整数分。
  • 原型仅在浏览器中模拟申请、审批、防重与余额变化；生产幂等、事务与银行号唯一性由后端保障。静态原型发布不等同真实资金部署或完成生产审查。

角色与状态

酒店管理员提交和分页查询本酒店申请；平台管理员、平台财务按酒店与审批状态查询并审批。酒店操作员、运营、司机、工厂角色不取得充值申请或审批权限。状态为 PENDING → APPROVED / REJECTED；通过时同一事务写入钱包、唯一账本及审批结果，驳回不入账，终态不允许改判。

接口与关联字段

  • POST /api/hotel/wallet/recharges：amount_cents、可选 description、idempotency_key；external_reference 为可选兼容字段，酒店表单不再要求填写或提交付款参考号。提交返回待审批记录；相同幂等键与相同内容重试返回原申请，内容冲突拒绝。
  • GET /api/hotel/wallet/recharges：按当前酒店隔离，支持 limit/offset 分页。
  • GET /api/admin/wallet/recharges：hotel_org_id、approval_status 与 limit/offset；审批状态支持 PENDING/APPROVED/REJECTED，不传表示全部。
  • GET /api/admin/wallet?hotel_org_id=...：独立查询所选酒店当前余额，不从分页流水推断余额。
  • POST /api/admin/wallet/recharges：平台登记待审批申请，新客户端提交 hotel_org_id、amount_cents、可选 description 与显式 idempotency_key，不再填写或提交付款参考号；旧 external_reference 仅用于兼容回退防重，不再直接入账。旧客户端必须随本次后端更新同步升级，不可把成功响应提示为到账。
  • POST /api/admin/wallet/recharges/{id}/review：approved、external_reference（通过时必填的核验银行流水号）、note（驳回时必填的原因）。同一核验银行流水不得跨申请或跨酒店重复入账。
  • 充值记录返回 id（充值业务 ID）、hotel_org_id、amount_cents、payment_reference（历史原始付款参考号，仅后台兼容保留，不在两端表单、列表或详情展示）、external_reference（核验银行流水号）、description、approval_status、wallet_entry_id、review_note、created_at、reviewed_at。待审批及驳回无入账流水 ID，不以申请 ID 冒充账本 ID。
  • 钱包流水补充 business_id、external_reference、approval_status，通过 wallet_entry_id 对应实际账本 id；原 business_key 仅在后台保留，用于内部关联和防重复入账；入账流水 ID、业务关联键及历史付款参考号均只在后台保留，不在 Web 与小程序界面展示。历史流水没有审批记录时关联业务 ID 和审批状态为空，页面明确展示历史未审批，不猜测或回填审批人。

手机账户展示

  • 余额卡下直接展示金额、可选备注与提交按钮，不再打开申请弹窗。记录列表以中文状态或业务类型、金额和时间紧凑展示，点击展开业务 ID、银行号、备注及审批说明。待审批和驳回申请可查；已通过申请与已加载的对应入账流水合并展示，尚未加载对应流水时保留已入账摘要；未入账申请不能套用钱包余额伪造变动后余额。Web 申请只选择酒店、填写金额与可选备注，两端均不输入或展示付款参考号；历史值仅后台兼容保留。审批通过仍必须核验并绑定银行流水号。账户记录按发生或申请时间合并倒序，整体无记录时显示“暂无账户流水”；实际客户端两类记录各按 20 条分页获取，静态原型合并后按每页 20 条展示。

联调验收

  1. 酒店申请 12.34 元，得到业务 ID 和待审批状态，余额、账本均不变。
  2. 财务核验并绑定带前导零和分隔符的银行流水号，通过后余额只增加 1234 分，申请与流水互相关联，两端一致。
  3. 拒绝申请必须填写原因，状态变为已驳回且不入账；终态不能改判。
  4. 验证网络重试、并发审批、同银行号跨申请及跨酒店操作均不重复入账；非法角色和跨酒店查询被拒绝。
  5. 申请成功及审批成功后自动更新相关列表和余额；失败保留输入，支持重试；分页不会把旧账本余额当作当前余额。
  6. 新增迁移保留原有账本，历史银行号不得被新审批再次核销；有申请记录的酒店与相关账号不得当作空资料删除。

资金变更仍须在合并或发布前完成双人人工审查；本地集成测试和智能体核验不替代该门禁。

正式系统边界

  • 正式服务升级需应用 v8 充值申请审批迁移并完成双人人工资金审查与后端集成测试；本次静态原型更新不执行迁移。运行系统既有测试记录见 fullstack 开发交接文档，不能作为本轮原型验收结果。

7. 基础资料删除与历史保护

  • 删除用于清理误建且无引用的基础资料，覆盖组织、酒店、工厂、站点、楼层、账号、司机、商品与种类；仅平台管理员和平台运营可操作，运营不得删除平台权限账号。逐条确认，不提供批量删除。
  • 组织有业务订单、资金流水、额度、协议价格、服务关系、扫描记录、非零余额，或成员有会话、历史业务及操作记录时拒绝删除。无业务空组织可连同无业务成员、楼层、地址和零余额空钱包清理，创建与删除审计保留。
  • 楼层有订单引用不可删除；工厂站点有服务关系、订单或扫描事件不可删除，酒店地址不允许作为独立工厂站点删除。状态停用不自动解除历史引用。
  • 账号有会话、业务或审计历史不可删除，当前登录账号、平台组织及最后一个启用管理员受保护。司机按账号规则校验，删除成功同时清理负责酒店分配。
  • 商品已有关联商城订单不可删除；种类已被商品使用不可删除。正式商品删除使用 DELETE /api/admin/store/products/{id}，其余基础资源通过受保护删除服务校验，不能直接删表或仅依赖前端禁用按钮。
  • 订单、退款、钱包账本、审计及扫描凭证保留；库存、结算和报表是汇总，不提供删除汇总行。协议价格继续调价维护。基础资料存在历史时使用适用的停用操作，不把“列表增加删除”解释为删除全部业务凭证。
  • 原型只能按示例状态演示“可删、保护阻止、确认取消、成功刷新”；数据库引用约束、并发校验与审计不能用原型本地行为替代验证。

8. 账号与密码规则

  • 酒店和工厂建档必须配置首个管理员；组织列表的独立成员弹窗添加成员时固定组织，用户列表按名称、角色、状态和组织查询分页。一个账号一个组织一个角色，不支持组织迁移或角色多选。
  • 平台管理员维护全部账号，平台运营仅维护非平台角色，财务只读。不得停用自己或降级自己的管理员角色；最后启用管理员不能降级、停用或删除；酒店最多 10 个启用账号。
  • 司机仅属于工厂，创建时同时配置负责酒店，不允许普通用户创建绕过分配，也不允许司机与其他角色互转。酒店移动端不提供员工管理，酒店成员由平台独立成员页面管理。
  • 新账号与重置密码统一手填密码和确认密码，8～20 位，英文字母、数字、英文半角特殊字符至少两类，不允许任何位置有空格、中文、全角字符、换行或表情；密码不裁剪。大小写字母同属一类。
  • 确认密码仅在客户端校验，不发送或保存；后端独立校验并 BCrypt 哈希保存。失败保留输入，成功或关闭清空密码；停用、角色变更或改密后原会话失效，恢复不复活旧会话，不自动启用停用账号。
